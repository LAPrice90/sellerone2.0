## What was meant to happen (the invariant)

### Canonical truth

1. **Level 1 creates the canonical order line keyset**: `(Order ID, SKU)` and provides:

   * Order purchase date (the “real order date”)
   * Quantity ordered (the only safe quantity source)
   * Market/country/currency context (directly or derivable)

2. **Level 2 and Level 3 only enrich those same keys**

   * L2 improves estimates
   * L3 replaces fees/sales with final finance values

### Order_Master rules that must always hold

* **Order_Master rows must be a subset of Level 1 keys** (or Level 1 + Level 2, if you explicitly allow L2-only, but never L3-only).
* **Order_Master.Date must come from Level 1** (purchase date), not from an L3 event timestamp.
* **Token allocation demand must come from Level 1 quantities**, not from L3 rows.

This is the only setup that prevents “finance rows” from being treated as “orders”.

## Why it is happening (mechanism)

### 1) Wrong join direction / wrong keyset construction

Your runbook says “if Level 3 exists use it”. That is fine **only if** Level 3 is treated as **enrichment**.

The likely code pattern in `B004_build_order_master.py` is something like:

* build a union/outer-join of keys across L1 + L2 + L3
* then pick best available values per column (fallback logic)

That is the critical mistake:

* Outer-joining keys lets Level 3 introduce brand-new `(Order ID, SKU)` lines that **never existed as Level 1 order items**.

### 2) Unsafe fallbacks for Date and Quantity

Once you allow L3-only keys into a merged dataset:

* `Date` falls back to the L3 event timestamp
* `Quantity Ordered` is missing (because L3 doesn’t have it), so code tends to default it

That makes “finance events” look like “orders”.

### 3) The health check is missing the exact orphan check

A015 currently checks:

* `l1_keys_missing_in_master` (L1 -> Master coverage)

But it does **not** check:

* `master_keys_missing_in_l1` (Master -> L1 legitimacy)
* or `l3_keys_missing_in_l1` (L3 orphans)

So the system can be internally corrupt while still passing the “coverage” test.

### 4) Knock-on effect: token allocation gets poisoned

Once phantom order lines exist, token allocation will:

* allocate tokens to them (stealing from real orders), or
* log massive shortages (blocking publish), or both.

This is exactly the mess you are feeling: downstream scripts are reacting correctly to bad upstream state.

## The fix that actually ends this (and stops future recurrence)

### Fix 1: Enforce the invariant in B004 (Order_Master build)

In `B004_build_order_master.py`:

* Define canonical keys from **Level 1 order items**: `(Order ID, SKU)`
* Join Level 2 onto that (left join)
* Join Level 3 onto that (left join)
* **Do not outer-join Level 3**
* Create a separate output:

  * `out/l3_orphans.csv` = rows in L3 whose keys do not exist in L1

Critical: **Order_Master.Date = Level 1 purchase date only**.
If L1 is missing for a key, that row does not belong in Order_Master.

### Fix 2: Enforce the invariant in B007 (token allocation)

In `B007_allocate_tokens_live.py`:

* The “demand” side must come from Level 1 quantities only
* Any row with missing quantity/date is **skipped and logged**, never allocated
* Never use L3-derived keys to drive allocation

### Fix 3: Make A015 catch this immediately

In `A015_build_system_health_check.py`, add:

* `l3_orphans_count` (FAIL if > 0, or WARN if you want a transition period)
* `order_master_orphans_count` (rows in Order_Master whose `(Order ID, SKU)` not in L1)
* `order_master_blank_qty` (FAIL if > 0)

This is the self-healing piece: once this exists, you can’t “silently drift” back into this state.
