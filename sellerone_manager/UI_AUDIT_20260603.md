# SellerOne UI Audit - 2026-06-03

## Plain English Verdict

The current UI is useful, but it is not yet a proper working surface for Luke.

It is a single Streamlit app called `Restocking Workspace`. It has real data and several good safety ideas, but it mixes too many jobs together:

- restocking
- product database viewing
- product database editing
- price-list scanner queue
- new product review
- brand approval
- repricer tracker
- PO drafts
- receiving
- send-to-Amazon handoff

That is why it feels messy. It is showing the construction site, not the finished office.

## What I Checked

- The UI is running locally on port 8501.
- The launcher is `run_O_operator_ui.bat`.
- The main UI file is `scripts/flows/O/O400_operator_ui.py`.
- The app has 13 top-level pages in a horizontal page selector.
- The UI is Streamlit, not a modern React or hosted Sites app.

## Current Screen Map

### Reorder

Purpose:

- shows supplier grouped reorder rows
- allows quantity and price entry
- sends local reorder events

Current issue:

- opens straight into work rows without a calm daily summary
- does not first explain what is ready, blocked, or unsafe
- supplier working is useful, but the page is too exposed as the default start

### Restock Session

Purpose:

- local restock review
- gathers supplier proof and blocker labels
- does not create purchase orders

Current evidence:

- 608 restock rows
- 35 suppliers
- 608 rows blocked from clean buy

Current issue:

- this is the best current foundation for manual restocking
- but it still shows proof machinery before it gives Luke a simple buying decision flow
- all rows being blocked means it is not yet ready for trusted ordering

### Product DB

Purpose:

- browse product truth
- Product DB Edit is separate for manual changes

Current evidence:

- 608 product rows
- 197 live
- 374 dropped
- 486 issues
- 608 stale

Current issue:

- this page cannot be treated as the clean daily product surface yet
- it needs clearer source freshness, issue grouping, and decision state
- stale product data should not be mixed with confident restocking decisions

### Price List Queue

Purpose:

- shows F scanner / price-list queue status

Current evidence:

- active scanner shown
- scanner state shown as running
- login/supervisor state exposed
- raw queue stats and large fail counts are visible

Current issue:

- this belongs under a maintenance/admin area, not in Luke's main business workflow
- Luke should not have to look at raw scanner chaos unless the manager says a decision is needed

### PO Drafts

Purpose:

- review local draft purchase order packets

Current evidence:

- 1 draft PO visible
- 1 line
- 15 units
- value around GBP 120.94

Current issue:

- useful, but it appears too late in a scattered chain
- it should become a step inside one buying workflow, not a separate top-level area at the same level as everything else

### Receiving

Purpose:

- record stock that has arrived

Current issue:

- this is a business action screen
- it should stay separate from restocking decisions, but it should be part of a clear "after purchase" workflow

### Send To Amazon

Purpose:

- record stock ready to send into Amazon

Current issue:

- also a business action screen
- should not sit beside scanner maintenance and product proof screens as if they are the same type of job

## Keep

Keep these foundations:

- Streamlit app as the short-term local UI
- Restock Session safety model
- local-only draft decisions
- supplier proof events
- pack/MOQ proof events
- purchase approval guardrails
- Product DB browse/edit separation
- price list queue visibility for admin use
- local PO draft preview
- receiving and send-to-Amazon event screens

## Fix

Fix these first:

- add a calm `Today` start page
- split business work from maintenance/admin work
- make Restocking the main manual buying workflow
- hide scanner internals from the main workflow
- label data as `ready`, `blocked`, `stale`, `not proven`, or `needs Luke`
- make Product DB freshness obvious before trusting product rows
- remove the long horizontal page selector as the main navigation
- stop showing proof machinery before the user has chosen a job

## Merge

Merge these into guided workflows:

- `Reorder` and `Restock Session` should become one manual restocking workflow
- `Purchase approval preview`, `Approval guardrails`, `PO readiness`, `PO line design`, `PO packet review`, and `PO hold review` should become one buying review lane
- `Receiving` and `Send to Amazon` should become one post-purchase stock movement lane
- scanner status should move into an admin/maintenance lane

## Park From Main UI

Do not delete these, but do not make them front-screen business pages:

- Price List Queue internals
- active scanner details
- login recovery state
- raw F queue controls
- repricer tracker write flags
- proof/debug accordions

These should be visible only in an admin/proof area or when the manager flags a real issue.

## First Rebuild Batch

### Batch 1 - Operator Shell

Goal:

- make the UI feel like a business tool instead of a pile of technical pages

Build:

- left navigation or clear section tabs
- `Today`
- `Restocking`
- `Products`
- `Suppliers`
- `Orders and P&L`
- `Receiving`
- `Proof/Admin`

Success:

- Luke opens the UI and immediately sees what business job is ready to work on
- scanner/maintenance details are not on the main path

### Batch 2 - Today Page

Goal:

- one calm first screen

Show:

- urgent restock count
- rows safe for manual review
- rows blocked and why
- suppliers with enough proof to work
- business decisions waiting for Luke
- manager/system blockers only if they affect today's work

Success:

- Luke does not need to open five pages to know what to do first

### Batch 3 - Manual Restocking Workspace

Goal:

- support Luke's manual restocking while O automation is still not trusted

Show each product with:

- supplier
- SKU/title/ASIN
- stock
- sales velocity
- buy cost
- Amazon price
- expected profit
- refund drag
- fee confidence
- inbound/FBA-send cost confidence
- supplier proof state
- pack/MOQ proof state
- recommended quantity
- blocker reason
- Luke decision

Success:

- a product cannot look order-ready unless the important proof fields are present
- Luke can still use the screen manually without automation pretending it is finished

### Batch 4 - Buying Review Lane

Goal:

- turn local drafts into a clear review process

Stages:

- draft decision
- supplier proof
- pack/MOQ proof
- purchase approval preview
- approval guardrail
- PO draft
- hold/reject/approve

Success:

- local drafts stay local
- no purchase order is treated as approved without Luke's decision

### Batch 5 - Admin/Proof Lane

Goal:

- keep technical proof available without flooding the business UI

Move here:

- price-list scanner queue
- F scanner login state
- raw proof tables
- repricer tracker proof
- system readiness tables

Success:

- the main UI stays calm
- the manager still has the proof it needs

## Sites / Hosted UI Position

Do not wait for Sites.

Use the current local Streamlit UI for the immediate cleanup. Sites may become useful later for hosting, access control, and saved deployments, but it should come after the workflow is clean.

## Immediate Recommendation

Do not build more random O screens yet.

Continue with `Batch 1 - Operator Shell`, then `Batch 2 - Today Page`, then `Batch 3 - Manual Restocking Workspace`.
