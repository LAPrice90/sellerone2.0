Architecture Design
Components and Workflow
The repricing system consists of several coordinated components running on a local machine, orchestrated by a background task scheduler. Below is a breakdown of the main components and their interactions:
Scheduler: A background task scheduler (e.g. Python’s APScheduler or Celery Beat) triggers various jobs at defined intervals. It coordinates periodic data fetch tasks, pricing evaluation tasks, and reporting tasks. The scheduler ensures tasks are spread out to avoid API rate limit bursts and can adjust frequencies dynamically.
Data Fetcher: A module responsible for calling Amazon SP-API endpoints to retrieve the latest data for products. It fetches pricing and competitive offer data, as well as periodic retrieval of inventory age, fees, and sales/refund reports. Fetched data is stored in a local database or cache for quick access by the strategy engine.
Pricing Strategy Engine: The core logic that evaluates each SKU’s situation and decides if a price change is needed. It uses per-SKU strategy rules and current data (our price, Buy Box price, competitor offers, costs/fees, etc.) to determine the optimal price that balances Buy Box win probability and profit. This engine factors in scenario flags (e.g. whether Amazon is a competitor, whether the current Buy Box winner is FBA or FBM) to apply the correct pricing rules. It also checks constraints like minimum margin and flags “unsavable” products that cannot win profitably.
Price Updater: This component takes the strategy engine’s pricing decisions and submits price updates to Amazon via SP-API. It may use either the Listings API (e.g. patchListingsItem for price updates) or feeds to update prices. The updater respects any Amazon-imposed throttle (e.g. max 1 price update per SKU per 10-15 seconds) by queuing updates and spacing them appropriately.
Local Data Store & Cache: A storage layer (e.g. a lightweight database like SQLite/PostgreSQL, with an in-memory cache for fast access) holds product info, strategy configurations, recent API responses, and history. This enables persistence of state (like last known competitor prices, last update timestamps) and quick reads without excessive API calls. A cache of last API call times per endpoint/SKU is maintained to calculate safe windows for the next call.
Logging & Reporting Module: Every pricing decision, API call, and outcome is logged. Logs are stored in a human-readable format (e.g. append-only log files or a “Decisions” table in the DB) with timestamps and details. A reporting sub-task periodically aggregates these logs to produce summary metrics (e.g. how many price changes per day, Buy Box win rate, new competitor identified) and alerts for notable events (like an SKU flagged as unsavable or a persistent undercutting competitor). Summaries can be output to console, stored as reports, or emailed, giving the user an at-a-glance view of system performance.

Pricing Strategy Engine Design
The pricing strategy engine is the brain of the repricing system. It applies a set of rules and algorithms per product to decide if and how to adjust the price. The design allows each SKU to have a tailored strategy aiming to maximize Buy Box ownership while maintaining profitability. Key aspects of the strategy engine include scenario-based rules, profit guardrails, and adaptability to competitor behavior.
Per-SKU Strategy Rules and Execution Flow
For each SKU, the strategy engine executes the following general flow when triggered:
Data Gathering: Retrieve the latest data for the SKU from the local store/cache – including our current price, the current Buy Box price and owner, and a list of competitor offers (price, seller type FBA/FBM, seller name/ID, stock if available). Also fetch any SKU-specific settings like minimum allowable price (floor), maximum price (ceiling), and cost/fee info for profit calculation.
Scenario Flag Evaluation: Determine which strategy scenarios are in effect by evaluating the data. For example:
Amazon Selling: True if Amazon Retail (sold by Amazon) is one of the competing sellers on this listing.
FBA Buy Box: True if the current Buy Box winner (featured offer) is an FBA seller (could be us or another FBA seller).
FBM Buy Box: True if the Buy Box is currently held by a FBM (merchant-fulfilled) seller, implying we might have a shipping advantage if we are FBA.
(Other flags can be defined as needed, e.g., Low Stock, High Price Elasticity, etc., but the above are the ones requested.)
These boolean flags are set to indicate the competitive scenario. Multiple flags can be true simultaneously (e.g., Amazon is selling and currently has the Buy Box, or Amazon is selling but an FBM seller holds the Buy Box, etc.). The flags will determine which subset of rules to apply.
Apply Pricing Rules: Based on the active flags and the SKU’s configured strategy, evaluate rules to decide on a new price. The rules can be seen as an if-else decision tree or a small rule engine. Examples of rule application:
If AmazonSelling = True: Amazon is a competitor on this listing. Strategy might dictate not trying to undercut Amazon aggressively if they have a price much lower than our cost (to avoid a race we can’t win). If Amazon’s price is only slightly below ours and we can afford a small cut, we might lower our price to just below Amazon’s to attempt Buy Box (keeping profit in mind). If Amazon holds the Buy Box and is far cheaper than our min price, the engine might decide this SKU is currently “unsavable” (we cannot compete) and mark it (see Unsavable logic below).
If FBA Buy Box = True: The Buy Box winner is an FBA seller (i.e., another FBA competitor or even Amazon). We likely need to price match or slightly beat the competitor’s price to win. The rule might be “set our price = competitor price - $0.01” (or -1 penny) to undercut if that’s above our minimum. However, if we already are the Buy Box winner (we’re FBA and currently winning), the strategy might instead consider raising our price gradually to increase profit until we lose the Buy Box (a technique to maximize profit while maintaining Buy Box).
If FBMBuyBox = True: A FBM competitor currently has the Buy Box. Since we fulfill via FBA, we have Prime shipping which often gives an edge. A rule here might be “we can match the FBM price or even price up to a small percentage higher (e.g. 5% higher) and still win due to faster delivery”. Thus, the engine could choose a price equal to the FBM price (to safely win) or slightly above if profit is a concern and we believe we’d still win the box (this could be tested over time).
General Under-cutting Rule: In competitor-based strategies, a common rule is to undercut the Buy Box price by the minimum increment (e.g., $0.01) if it doesn’t violate profit margins. The engine will ensure any new price >= minimum allowed price. If undercutting would go below cost or minimum margin, it will either keep the price or only match the competitor. Profit protection is critical – the system will not chase the Buy Box below a floor price that ensures at least, say, 5% margin or a few dollars profit.
Raise Price Opportunity: If our offer currently holds the Buy Box at a price higher than our minimum (meaning we have room to spare), and competitors are out-of-stock or significantly higher, the engine might raise our price towards the next highest competitor or a defined ceiling, to maximize profit while still holding the Buy Box. (This is an advanced behavior for when competition vanishes or we’re dominating the listing.)
Unsavable SKU Logic: As part of rule evaluation, the engine checks if the SKU is “unsavable” under current conditions. An unsavable scenario is when our offer cannot realistically win the Buy Box at a profitable price. Indicators include: our minimum profitable price is higher than the Buy Box price by a large margin (due to high FBA fees or a competitor with a much lower cost base), or the Buy Box is held by Amazon at a price near or below our cost. If these conditions persist, the engine will mark a flag on that SKU (e.g., unsavable=True) and log a warning. The strategy for unsavables could be to stop further price decreases (no “race to bottom”), and possibly trigger an alert to review this SKU (maybe we consider removing it from FBA or waiting for a better time). Unsavable SKUs might be periodically revisited to see if conditions change (e.g., competitor goes out of stock, allowing a profitable sale at our price).
Decision Output: The engine produces a decision – either “keep price as is” or “new price = X”. It also attaches a rationale (which rule fired, which competitor we’re responding to, etc.) for logging. If a price change is recommended, this decision is passed to the Price Updater component to execute the update via API. The whole decision (old price, new price, reason, flags, competitor data) is sent to the Logger as well.
The strategy execution is designed to be fast (low latency) since it may be reacting to real-time changes. We want the end-to-end loop (fetch data -> decide -> update price) to be quick, ideally a few seconds. This ensures we don’t miss short-lived opportunities. A low-latency decision cycle, combined with stable throughput of API calls, is crucial because repricing is highly time-sensitive

Rate Limiting and Caching Mechanism
Efficient use of API quotas and timely responses rely on a robust rate limiting and caching mechanism. This subsystem works behind the scenes to support the scheduler and strategy engine:
API Rate Limit Tracker: The system maintains a global registry of API endpoints with their known rate limits (from Amazon’s documentation or responses). Each time an API call is made, it records the timestamp and decrement the available “token” count for that endpoint. A background process or the scheduler monitors these timestamps. For example, if getCompetitiveSummary allows 10 calls per minute (hypothetical), the tracker will ensure we do not exceed this by delaying or queueing calls. If a call is attempted and the limit would be exceeded, the call is deferred until the next available window. This can be implemented with a token bucket or leaky bucket algorithm, or simply by computing next allowed time. The cache of last-call times per SKU per operation is also kept, so we avoid, say, fetching the same SKU’s data twice in very short succession unless an external event warranted it.
Caching of Responses: Recently fetched data (like the competitive summary for a SKU) is stored in memory or a fast cache layer (with a copy in the DB if persistence needed). This cache entry might include a TTL (time-to-live). If the strategy engine requests data for a SKU that was just fetched 30 seconds ago and no significant event occurred, the system can use the cached data instead of calling the API again, to reduce calls. This is especially useful for data that doesn’t change second-to-second (inventory age, fees, etc. can be cached for hours). However, pricing data is time-sensitive; caching is used carefully there – for example, cache competitive prices for a minute, but if a new decision cycle comes after a minute, likely refresh from API to avoid missing a competitor’s price change. The caching strategy thus preserves precision without sacrificing freshness
flashpricer.com
 by choosing appropriate TTLs per data type (short TTL for price data, long TTL for static data).
Filling Call Gaps: As discussed, when a particular SKU is on cooldown (e.g., we just updated its price and don’t want to call again immediately), the scheduler will pick another SKU to operate on. The cache/tracker helps by providing a list of “allowed calls” at any given second. For instance, if only 1 price update per 15 seconds per SKU is allowed but we have 10 SKUs needing updates, the system can update SKU1, then in the next second update SKU2, and so on, cycling through until SKU1’s 15 seconds have passed. Similarly, if getCompetitiveSummary calls are limited to, say, 30 calls/hour, the system spreads them out (about one every 2 minutes) and might batch 20 SKUs in each to cover all SKUs in that hour. Any idle time is avoided by adjusting task frequencies – if at some moment no SKU needs immediate attention, the system can either wait or use the time to do lower-priority updates (like fetch a daily report).
Error Handling and Backoff: If the SP-API returns a throttle error or any failure, the system’s rate limiter catches it and backs off appropriately. It logs these events. If a burst of calls triggered a limit, the scheduler can pause certain tasks briefly and then resume. The cache may mark data as stale if an update failed, and those SKUs might be retried sooner once allowed.
Overall, this mechanism acts like a traffic cop, ensuring we never hit Amazon’s hard limits (which could result in request failures or API penalties) while still making as many calls as needed for real-time performance. Debugging and Analysis: to understand why the system made a particular decision (useful for tweaking strategies).
Performance Monitoring: to track how often we’re winning the Buy Box, how often prices change, and identify any issues (like thrashing prices or prolonged Buy Box loss).

Competitor Overview: A brief summary of key competitors, e.g., “Amazon at £19.99, FBM seller at £20.49 (shipping not Prime)”.
Flags/Scenario: Which scenario flags were true, e.g., “[AmazonSelling=False, FBMBuyBox=True]”.
Decision Rationale: A message describing the action: e.g., “Matched FBM competitor price to win Buy Box (we have Prime advantage)” or “No change – our price is lowest, holding Buy Box” or “Price lowered from £15.00 to £14.80 to undercut competitor X by £0.01”. In case of no change: “Kept price; undercutting would violate min margin.”
Outcome/Result: If known immediately or later, note the outcome such as “Buy Box won” or “Still second place”. (Immediate outcome might not always be available unless we query again; this could be updated on next cycle or inferred from notifications.)
Action Type: e.g., “Price Update API called” or “No update needed”. If an update API was called, we also log success/failure of that API call.
These logs are written in a human-readable form. For example, a log line might look like:
2025-12-02 10:15:00 SKU1234: Price £19.99 -> £19.50. Flags[AmazonSelling=False, FBABuyBox=True]. Lowered price by £0.49 to beat competitor (FBA competitor was £19.99). Buy Box expected to win.  
Or if no change:
2025-12-02 10:15:00 SKU5678: Price £15.00 unchanged. Flags[AmazonSelling=True, FBMBuyBox=False]. Amazon at £12.99 - below cost, marked unsavable.  
All API calls are also logged (at least at a summary level), for example: “Called getCompetitiveSummary for 20 SKUs (IDs)…”, “Patched price for SKU1234 to £19.50 – SUCCESS”. This helps track our API usage and detect any call failures or throttling events.
Summary Reports and Alerts
In addition to the granular log, the system generates periodic summary reports to highlight overall performance and any important events:
Buy Box Win Rate: The percentage of time (or of checks) each SKU is in the Buy Box. This can be computed from competitive data or notifications. A daily summary might say “Buy Box held for 80% of checks across all SKUs today. Notable losers: SKU XYZ lost Buy Box 10 times to competitor ABC.”
Price Changes Count: How many price updates were made per SKU per day, and overall. E.g., “Total 50 price adjustments today (0.48 per SKU on average). SKU123 had 5 changes (high competition).” This can reveal if a SKU is “thrashing” (too many changes) which might warrant strategy adjustment.
New Competitors or Scenarios: If a new competitor appears on a listing for the first time, or if Amazon itself joins a listing, the system flags that. For example, “New competitor detected on SKU789: Seller ‘BestDeals’ (FBM) entered at £10.99.” Or “Amazon is now selling SKU101 (was previously third-party only). Strategy flag AmazonSelling activated.” Such events are important for the user to know.
Unsavable SKU Alerts: If any SKU was flagged as unsavable during the day, highlight it: “SKU5678 flagged unsavable – Buy Box price below our cost due to fees. Recommended to review this SKU’s viability.”
Performance & Errors: Report any API throttling incidents or errors. E.g., “Hit rate limit 3 times today on competitive price fetch – consider reducing frequency or batching more.” Also include latency stats if relevant (e.g., average decision cycle time).
Revenue/Sales Impact (optional): If sales data is integrated, report on sales achieved and if repricing had an obvious effect. For example, “SKU1234 sold 10 units after aggressive repricing, clearing 50% of aged inventory.”
These summaries are designed to be human-readable and could be delivered as daily emails or printed to console/log. They condense the day’s activity so the user doesn’t have to sift through detailed logs unless needed. The logs and reports follow a structured format (so they can be parsed or analyzed further), but are also meant to be readable. For instance, the system might use a simple markdown or table format for daily reports if emailed, or just plain text bullet points.
Logging Implementation
Under the hood, logging can be done using Python’s logging library, writing to rotating log files. A separate “analysis” thread or scheduled task can query the database for interesting events (like unsavable flags set, or count of price changes) to compile the summary. The logs can also serve as training data if in the future an AI model is introduced (the AI could learn from historical decisions and outcomes). All logging and reporting events also increment counters or update state in the data store (for example, a counter for how many times competitor X undercut us today, to facilitate competitor modeling described next).
Data Storage and Strategy State Management
A structured approach to data storage ensures that the system can quickly access current state and also analyze historical trends. We recommend using a relational database (like SQLite for simplicity, or PostgreSQL/MySQL if scaling up) combined with an in-memory cache for hot data. The schema might include tables or collections for:
Products Table: List of SKUs/ASINs under management. Fields: SKU, ASIN, product title, cost (our buy cost), min_price, max_price, etc., and flags for strategy (AmazonSelling, FBABuyBox, etc. – though these particular flags are dynamic state updated each cycle and might reside in a state table instead). Also store static info like FBA fees (if known per unit) and dimensions that affect fees.
Strategy Configs: Could be combined with Products table or separate. This holds the per-SKU strategy parameters: e.g., which repricing strategy type is assigned (if we have named strategies), the minimum margin percentage allowed, whether aggressive mode is on, etc. It can also include boolean fields for toggling strategies like “allow price increase” or “only match not undercut” for certain scenarios. Essentially, this is where the user’s preferences per SKU are stored.
Current State Table: This table holds the most recent dynamic data for each SKU, updated after each API fetch. Fields might include: last known buy box price, buy box owner, our current price, our last update time, our stock level, total competitor count, lowest competitor price, etc. The scenario flags (AmazonSelling, FBMBuyBox, etc.) can also be stored here for quick reference and debugging. This table is essentially overwritten or upserted each cycle with fresh data. By having this in a table, the strategy engine can query many SKUs at once if needed (for example, to find all SKUs where we lost Buy Box, if we wanted to batch decisions).
Historical Price/Competition Table: A log of key metrics over time for analysis. Each entry could record, say, on each significant event or time interval: SKU, timestamp, our price, buy box price, competitor count, our buy box status (won/lost), etc. This would grow over time and could be used for trend analysis (e.g., seeing how often price wars happen, or how a competitor’s price moves). We might not log every single check to avoid enormous data, but maybe only when things change or on a timed interval (e.g., snapshot once an hour per SKU).
Decision Log Table: As described in logging, we might store structured fields for each price decision made. This might overlap with the Historical table above, but includes the specific action taken and rationale. Storing it in a table (in addition to flat log file) allows running queries like “show all cases where we lowered price but still didn’t get Buy Box” etc., which is useful to refine strategies.
Competitor Info Table (Optional Advanced): If we want to model competitor behavior, we can have a table keyed by Competitor (seller ID) and SKU, storing information like how many times that competitor was observed holding the Buy Box, average price, how often they change price, last seen price, and any pattern notes. For example, competitor X on SKU Y tends to undercut by 1p and changes price 5 times a day, etc. This is populated from the competitive data we fetch. Over time, this becomes a rich dataset of competitor behaviors.
All these tables together form our internal knowledge base. The data store doesn’t need to be overly complex given the scale (hundreds of SKUs), but designing it with clarity ensures we can scale to thousands of SKUs in future. The cache layer (e.g., a dictionary or a Redis if needed) would mirror some of this data in memory for quick access, especially the Current State for each SKU and the last API call times. Storage and Retrieval Operations: Typical operations include:
On fetching new data for SKU(s), update the Current State table and append to Historical table.
The strategy engine reads from Current State (and possibly Strategy Config) for its logic.
When a SKU is flagged unsavable or a strategy flag changes, update the Products/Config tables so that state persists.
When logging decisions, insert into Decision Log table.
Periodic archival: older historical data could be archived or pruned if space is a concern (or kept indefinitely for AI training possibilities).

Design Plan: Local Python-Based Amazon Repricing System
System Overview
This document outlines a technical design for a Python-based Amazon repricing system that runs locally using background task schedulers. The system manages pricing for ~104 FBA products (with potential for growth) by leveraging Amazon’s Selling Partner API (SP-API) to gather product data (pricing, competitive offers, inventory age, fees, sales/refunds) and to update prices. The design emphasizes continuous data fetching at optimal intervals, per-SKU pricing strategies to maximize Buy Box ownership and profitability, and a robust scheduling, caching, and logging framework. Key features include:
Continuous Data Fetching: Intelligent polling of pricing & competitive data, balancing API throttling with time-sensitive price updates.
Per-Product Strategy Rules: Customizable rules (per SKU) to adjust prices for Buy Box wins and profit maximization.
Rate Limiting & Caching: Tracking API call timestamps to respect rate limits and fill idle periods with calls for other SKUs.
Scenario Tagging: Use of boolean strategy flags (e.g. Amazon Selling, FBA Buy Box, FBM Buy Box) to mark scenarios and tailor pricing behavior.
Decision Logging: Detailed logs of all pricing decisions, actions, and outcomes for analysis and future tuning.
Competitor Behavior Adaptation: Framework to detect competitor pricing patterns (e.g. constant undercutting) and adapt strategy (e.g. aggressive response to specific sellers).
Unsavable SKU Flagging: Identification of SKUs that cannot compete profitably (due to fees, delivery disadvantages, etc.) for potential deactivation or alternate handling.
Summary Reporting: Human-readable summaries of actions taken, new scenarios identified, and system performance metrics (delivered via logs or alerts).
Extensibility: A modular design allowing future integration of AI-driven strategy selection or reinforcement learning components.
This plan is structured into sections covering the overall architecture, API usage patterns and scheduling, strategy engine design, data storage, logging/reporting, and optional advanced components.
Architecture Design
Components and Workflow
The repricing system consists of several coordinated components running on a local machine, orchestrated by a background task scheduler. Below is a breakdown of the main components and their interactions:
Scheduler: A background task scheduler (e.g. Python’s APScheduler or Celery Beat) triggers various jobs at defined intervals. It coordinates periodic data fetch tasks, pricing evaluation tasks, and reporting tasks. The scheduler ensures tasks are spread out to avoid API rate limit bursts and can adjust frequencies dynamically.
Data Fetcher: A module responsible for calling Amazon SP-API endpoints to retrieve the latest data for products. It fetches pricing and competitive offer data, as well as periodic retrieval of inventory age, fees, and sales/refund reports. Fetched data is stored in a local database or cache for quick access by the strategy engine.
Pricing Strategy Engine: The core logic that evaluates each SKU’s situation and decides if a price change is needed. It uses per-SKU strategy rules and current data (our price, Buy Box price, competitor offers, costs/fees, etc.) to determine the optimal price that balances Buy Box win probability and profit. This engine factors in scenario flags (e.g. whether Amazon is a competitor, whether the current Buy Box winner is FBA or FBM) to apply the correct pricing rules. It also checks constraints like minimum margin and flags “unsavable” products that cannot win profitably.
Price Updater: This component takes the strategy engine’s pricing decisions and submits price updates to Amazon via SP-API. It may use either the Listings API (e.g. patchListingsItem for price updates) or feeds to update prices. The updater respects any Amazon-imposed throttle (e.g. max 1 price update per SKU per 10-15 seconds) by queuing updates and spacing them appropriately.
Local Data Store & Cache: A storage layer (e.g. a lightweight database like SQLite/PostgreSQL, with an in-memory cache for fast access) holds product info, strategy configurations, recent API responses, and history. This enables persistence of state (like last known competitor prices, last update timestamps) and quick reads without excessive API calls. A cache of last API call times per endpoint/SKU is maintained to calculate safe windows for the next call.
Logging & Reporting Module: Every pricing decision, API call, and outcome is logged. Logs are stored in a human-readable format (e.g. append-only log files or a “Decisions” table in the DB) with timestamps and details. A reporting sub-task periodically aggregates these logs to produce summary metrics (e.g. how many price changes per day, Buy Box win rate, new competitor identified) and alerts for notable events (like an SKU flagged as unsavable or a persistent undercutting competitor). Summaries can be output to console, stored as reports, or emailed, giving the user an at-a-glance view of system performance.

, ensuring instant reactivity to critical changes. API Call Throttling and Fill-Rate: All API calls include timestamp logging in the cache. Before any call, the system checks the last call time and the endpoint’s rate limit rules. For instance, if patchListingsItem allows 5 calls per minute, after one price update, the system knows the next update call slot is 12 seconds later (60/5). It then utilizes the interim by executing other tasks or calls for different SKUs. By caching each SKU’s last update time, the scheduler can round-robin through SKUs that need updates, ensuring no single SKU is updated more frequently than allowed (e.g., one product’s price update every 15 seconds as given in the example scenario). In effect, if SKU1’s price was just updated, the system will shift to update SKU2, SKU3, etc., then come back to SKU1 when its 15-second window passes. This prevents idle time – the system is always doing a useful call for some SKU as long as there’s any pending action, thus filling the gaps with other SKUs’ operations.
Pricing Strategy Engine Design
The pricing strategy engine is the brain of the repricing system. It applies a set of rules and algorithms per product to decide if and how to adjust the price. The design allows each SKU to have a tailored strategy aiming to maximize Buy Box ownership while maintaining profitability. Key aspects of the strategy engine include scenario-based rules, profit guardrails, and adaptability to competitor behavior.
Per-SKU Strategy Rules and Execution Flow
For each SKU, the strategy engine executes the following general flow when triggered:
Data Gathering: Retrieve the latest data for the SKU from the local store/cache – including our current price, the current Buy Box price and owner, and a list of competitor offers (price, seller type FBA/FBM, seller name/ID, stock if available). Also fetch any SKU-specific settings like minimum allowable price (floor), maximum price (ceiling), and cost/fee info for profit calculation.
Scenario Flag Evaluation: Determine which strategy scenarios are in effect by evaluating the data. For example:
Amazon Selling: True if Amazon Retail (sold by Amazon) is one of the competing sellers on this listing.
FBA Buy Box: True if the current Buy Box winner (featured offer) is an FBA seller (could be us or another FBA seller).
FBM Buy Box: True if the Buy Box is currently held by a FBM (merchant-fulfilled) seller, implying we might have a shipping advantage if we are FBA.
(Other flags can be defined as needed, e.g., Low Stock, High Price Elasticity, etc., but the above are the ones requested.)
These boolean flags are set to indicate the competitive scenario. Multiple flags can be true simultaneously (e.g., Amazon is selling and currently has the Buy Box, or Amazon is selling but an FBM seller holds the Buy Box, etc.). The flags will determine which subset of rules to apply.
Apply Pricing Rules: Based on the active flags and the SKU’s configured strategy, evaluate rules to decide on a new price. The rules can be seen as an if-else decision tree or a small rule engine. Examples of rule application:
If AmazonSelling = True: Amazon is a competitor on this listing. Strategy might dictate not trying to undercut Amazon aggressively if they have a price much lower than our cost (to avoid a race we can’t win). If Amazon’s price is only slightly below ours and we can afford a small cut, we might lower our price to just below Amazon’s to attempt Buy Box (keeping profit in mind). If Amazon holds the Buy Box and is far cheaper than our min price, the engine might decide this SKU is currently “unsavable” (we cannot compete) and mark it (see Unsavable logic below).
If FBA Buy Box = True: The Buy Box winner is an FBA seller (i.e., another FBA competitor or even Amazon). We likely need to price match or slightly beat the competitor’s price to win. The rule might be “set our price = competitor price - $0.01” (or -1 penny) to undercut if that’s above our minimum. However, if we already are the Buy Box winner (we’re FBA and currently winning), the strategy might instead consider raising our price gradually to increase profit until we lose the Buy Box (a technique to maximize profit while maintaining Buy Box).
If FBMBuyBox = True: A FBM competitor currently has the Buy Box. Since we fulfill via FBA, we have Prime shipping which often gives an edge. A rule here might be “we can match the FBM price or even price up to a small percentage higher (e.g. 5% higher) and still win due to faster delivery”. Thus, the engine could choose a price equal to the FBM price (to safely win) or slightly above if profit is a concern and we believe we’d still win the box (this could be tested over time).
General Under-cutting Rule: In competitor-based strategies, a common rule is to undercut the Buy Box price by the minimum increment (e.g., $0.01) if it doesn’t violate profit margins. The engine will ensure any new price >= minimum allowed price. If undercutting would go below cost or minimum margin, it will either keep the price or only match the competitor. Profit protection is critical – the system will not chase the Buy Box below a floor price that ensures at least, say, 5% margin or a few dollars profit.
Raise Price Opportunity: If our offer currently holds the Buy Box at a price higher than our minimum (meaning we have room to spare), and competitors are out-of-stock or significantly higher, the engine might raise our price towards the next highest competitor or a defined ceiling, to maximize profit while still holding the Buy Box. (This is an advanced behavior for when competition vanishes or we’re dominating the listing.)
Unsavable SKU Logic: As part of rule evaluation, the engine checks if the SKU is “unsavable” under current conditions. An unsavable scenario is when our offer cannot realistically win the Buy Box at a profitable price. Indicators include: our minimum profitable price is higher than the Buy Box price by a large margin (due to high FBA fees or a competitor with a much lower cost base), or the Buy Box is held by Amazon at a price near or below our cost. If these conditions persist, the engine will mark a flag on that SKU (e.g., unsavable=True) and log a warning. The strategy for unsavables could be to stop further price decreases (no “race to bottom”), and possibly trigger an alert to review this SKU (maybe we consider removing it from FBA or waiting for a better time). Unsavable SKUs might be periodically revisited to see if conditions change (e.g., competitor goes out of stock, allowing a profitable sale at our price).
Decision Output: The engine produces a decision – either “keep price as is” or “new price = X”. It also attaches a rationale (which rule fired, which competitor we’re responding to, etc.) for logging. If a price change is recommended, this decision is passed to the Price Updater component to execute the update via API. The whole decision (old price, new price, reason, flags, competitor data) is sent to the Logger as well.
The strategy execution is designed to be fast (low latency) since it may be reacting to real-time changes. We want the end-to-end loop (fetch data -> decide -> update price) to be quick, ideally a few seconds. This ensures we don’t miss short-lived opportunities. A low-latency decision cycle, combined with stable throughput of API calls, is crucial because repricing is highly time-sensitive

Strategy Tagging and Scenario Flags
The system uses scenario flags to make the decision logic transparent and configurable. For each SKU, the current state of these flags can be logged (e.g., “SKU123: AmazonSelling=False, FBABuyBox=True, FBMBuyBox=False”) alongside the decision, which helps in debugging and tuning strategy. Moreover, these flags allow the user to tag and filter SKUs by scenario. For instance, one could query all SKUs where AmazonSelling=True to identify products competing with Amazon, and perhaps apply a more conservative global strategy to them (since competing with Amazon often requires different tactics). Under the hood, these flags are determined either by real-time data (e.g., seeing Amazon as a seller in the competitive summary sets AmazonSelling=True automatically) or by some configuration. The system design allows future addition of more flags or strategy tags. All flags and strategy parameters for each SKU are stored in the data store, so they persist across runs and can be edited via a config UI or file.

Rate Limiting and Caching Mechanism
Efficient use of API quotas and timely responses rely on a robust rate limiting and caching mechanism. This subsystem works behind the scenes to support the scheduler and strategy engine:
API Rate Limit Tracker: The system maintains a global registry of API endpoints with their known rate limits (from Amazon’s documentation or responses). Each time an API call is made, it records the timestamp and decrement the available “token” count for that endpoint. A background process or the scheduler monitors these timestamps. For example, if getCompetitiveSummary allows 10 calls per minute (hypothetical), the tracker will ensure we do not exceed this by delaying or queueing calls. If a call is attempted and the limit would be exceeded, the call is deferred until the next available window. This can be implemented with a token bucket or leaky bucket algorithm, or simply by computing next allowed time. The cache of last-call times per SKU per operation is also kept, so we avoid, say, fetching the same SKU’s data twice in very short succession unless an external event warranted it.
Caching of Responses: Recently fetched data (like the competitive summary for a SKU) is stored in memory or a fast cache layer (with a copy in the DB if persistence needed). This cache entry might include a TTL (time-to-live). If the strategy engine requests data for a SKU that was just fetched 30 seconds ago and no significant event occurred, the system can use the cached data instead of calling the API again, to reduce calls. This is especially useful for data that doesn’t change second-to-second (inventory age, fees, etc. can be cached for hours). However, pricing data is time-sensitive; caching is used carefully there – for example, cache competitive prices for a minute, but if a new decision cycle comes after a minute, likely refresh from API to avoid missing a competitor’s price change. The caching strategy thus preserves precision without sacrificing freshness
flashpricer.com
 by choosing appropriate TTLs per data type (short TTL for price data, long TTL for static data).
Filling Call Gaps: As discussed, when a particular SKU is on cooldown (e.g., we just updated its price and don’t want to call again immediately), the scheduler will pick another SKU to operate on. The cache/tracker helps by providing a list of “allowed calls” at any given second. For instance, if only 1 price update per 15 seconds per SKU is allowed but we have 10 SKUs needing updates, the system can update SKU1, then in the next second update SKU2, and so on, cycling through until SKU1’s 15 seconds have passed. Similarly, if getCompetitiveSummary calls are limited to, say, 30 calls/hour, the system spreads them out (about one every 2 minutes) and might batch 20 SKUs in each to cover all SKUs in that hour. Any idle time is avoided by adjusting task frequencies – if at some moment no SKU needs immediate attention, the system can either wait or use the time to do lower-priority updates (like fetch a daily report).
Error Handling and Backoff: If the SP-API returns a throttle error or any failure, the system’s rate limiter catches it and backs off appropriately. It logs these events. If a burst of calls triggered a limit, the scheduler can pause certain tasks briefly and then resume. The cache may mark data as stale if an update failed, and those SKUs might be retried sooner once allowed.
Overall, this mechanism acts like a traffic cop, ensuring we never hit Amazon’s hard limits (which could result in request failures or API penalties) while still making as many calls as needed for real-time performance. The careful orchestration of calls, guided by caching models and internal routing logic, achieves the goal of maintaining repricing speed and responsiveness without waste

Logging and Reporting
Every action the repricing system takes is logged for audit and analysis. Logging serves two purposes:
Debugging and Analysis: to understand why the system made a particular decision (useful for tweaking strategies).
Performance Monitoring: to track how often we’re winning the Buy Box, how often prices change, and identify any issues (like thrashing prices or prolonged Buy Box loss).
Decision and Action Logs
Each price evaluation cycle for a SKU produces a log entry. The log is written to a text file and/or a database table. A log entry contains fields such as:
Timestamp: Date/time of the decision.
SKU/ASIN: Identifier of the product.
Current Price (Before): Our price before change.
New Price (After): Our price after change (or “(no change)” if none made).
Buy Box Price & Seller: The Buy Box price at the time and who held it (e.g., competitor’s ID or “us”).
Competitor Overview: A brief summary of key competitors, e.g., “Amazon at £19.99, FBM seller at £20.49 (shipping not Prime)”.
Flags/Scenario: Which scenario flags were true, e.g., “[AmazonSelling=False, FBMBuyBox=True]”.
Decision Rationale: A message describing the action: e.g., “Matched FBM competitor price to win Buy Box (we have Prime advantage)” or “No change – our price is lowest, holding Buy Box” or “Price lowered from £15.00 to £14.80 to undercut competitor X by £0.01”. In case of no change: “Kept price; undercutting would violate min margin.”
Outcome/Result: If known immediately or later, note the outcome such as “Buy Box won” or “Still second place”. (Immediate outcome might not always be available unless we query again; this could be updated on next cycle or inferred from notifications.)
Action Type: e.g., “Price Update API called” or “No update needed”. If an update API was called, we also log success/failure of that API call.
These logs are written in a human-readable form. For example, a log line might look like:
2025-12-02 10:15:00 SKU1234: Price £19.99 -> £19.50. Flags[AmazonSelling=False, FBABuyBox=True]. Lowered price by £0.49 to beat competitor (FBA competitor was £19.99). Buy Box expected to win.  
Or if no change:
2025-12-02 10:15:00 SKU5678: Price £15.00 unchanged. Flags[AmazonSelling=True, FBMBuyBox=False]. Amazon at £12.99 - below cost, marked unsavable.  
All API calls are also logged (at least at a summary level), for example: “Called getCompetitiveSummary for 20 SKUs (IDs)…”, “Patched price for SKU1234 to £19.50 – SUCCESS”. This helps track our API usage and detect any call failures or throttling events.
Summary Reports and Alerts
In addition to the granular log, the system generates periodic summary reports to highlight overall performance and any important events:
Buy Box Win Rate: The percentage of time (or of checks) each SKU is in the Buy Box. This can be computed from competitive data or notifications. A daily summary might say “Buy Box held for 80% of checks across all SKUs today. Notable losers: SKU XYZ lost Buy Box 10 times to competitor ABC.”
Price Changes Count: How many price updates were made per SKU per day, and overall. E.g., “Total 50 price adjustments today (0.48 per SKU on average). SKU123 had 5 changes (high competition).” This can reveal if a SKU is “thrashing” (too many changes) which might warrant strategy adjustment.
New Competitors or Scenarios: If a new competitor appears on a listing for the first time, or if Amazon itself joins a listing, the system flags that. For example, “New competitor detected on SKU789: Seller ‘BestDeals’ (FBM) entered at £10.99.” Or “Amazon is now selling SKU101 (was previously third-party only). Strategy flag AmazonSelling activated.” Such events are important for the user to know.
Unsavable SKU Alerts: If any SKU was flagged as unsavable during the day, highlight it: “SKU5678 flagged unsavable – Buy Box price below our cost due to fees. Recommended to review this SKU’s viability.”
Performance & Errors: Report any API throttling incidents or errors. E.g., “Hit rate limit 3 times today on competitive price fetch – consider reducing frequency or batching more.” Also include latency stats if relevant (e.g., average decision cycle time).
Revenue/Sales Impact (optional): If sales data is integrated, report on sales achieved and if repricing had an obvious effect. For example, “SKU1234 sold 10 units after aggressive repricing, clearing 50% of aged inventory.”
These summaries are designed to be human-readable and could be delivered as daily emails or printed to console/log. They condense the day’s activity so the user doesn’t have to sift through detailed logs unless needed. The logs and reports follow a structured format (so they can be parsed or analyzed further), but are also meant to be readable. For instance, the system might use a simple markdown or table format for daily reports if emailed, or just plain text bullet points.
Logging Implementation
Under the hood, logging can be done using Python’s logging library, writing to rotating log files. A separate “analysis” thread or scheduled task can query the database for interesting events (like unsavable flags set, or count of price changes) to compile the summary. The logs can also serve as training data if in the future an AI model is introduced (the AI could learn from historical decisions and outcomes). All logging and reporting events also increment counters or update state in the data store (for example, a counter for how many times competitor X undercut us today, to facilitate competitor modeling described next).
Data Storage and Strategy State Management
A structured approach to data storage ensures that the system can quickly access current state and also analyze historical trends. We recommend using a relational database (like SQLite for simplicity, or PostgreSQL/MySQL if scaling up) combined with an in-memory cache for hot data. The schema might include tables or collections for:
Products Table: List of SKUs/ASINs under management. Fields: SKU, ASIN, product title, cost (our buy cost), min_price, max_price, etc., and flags for strategy (AmazonSelling, FBABuyBox, etc. – though these particular flags are dynamic state updated each cycle and might reside in a state table instead). Also store static info like FBA fees (if known per unit) and dimensions that affect fees.
Strategy Configs: Could be combined with Products table or separate. This holds the per-SKU strategy parameters: e.g., which repricing strategy type is assigned (if we have named strategies), the minimum margin percentage allowed, whether aggressive mode is on, etc. It can also include boolean fields for toggling strategies like “allow price increase” or “only match not undercut” for certain scenarios. Essentially, this is where the user’s preferences per SKU are stored.
Current State Table: This table holds the most recent dynamic data for each SKU, updated after each API fetch. Fields might include: last known buy box price, buy box owner, our current price, our last update time, our stock level, total competitor count, lowest competitor price, etc. The scenario flags (AmazonSelling, FBMBuyBox, etc.) can also be stored here for quick reference and debugging. This table is essentially overwritten or upserted each cycle with fresh data. By having this in a table, the strategy engine can query many SKUs at once if needed (for example, to find all SKUs where we lost Buy Box, if we wanted to batch decisions).
Historical Price/Competition Table: A log of key metrics over time for analysis. Each entry could record, say, on each significant event or time interval: SKU, timestamp, our price, buy box price, competitor count, our buy box status (won/lost), etc. This would grow over time and could be used for trend analysis (e.g., seeing how often price wars happen, or how a competitor’s price moves). We might not log every single check to avoid enormous data, but maybe only when things change or on a timed interval (e.g., snapshot once an hour per SKU).
Decision Log Table: As described in logging, we might store structured fields for each price decision made. This might overlap with the Historical table above, but includes the specific action taken and rationale. Storing it in a table (in addition to flat log file) allows running queries like “show all cases where we lowered price but still didn’t get Buy Box” etc., which is useful to refine strategies.
Competitor Info Table (Optional Advanced): If we want to model competitor behavior, we can have a table keyed by Competitor (seller ID) and SKU, storing information like how many times that competitor was observed holding the Buy Box, average price, how often they change price, last seen price, and any pattern notes. For example, competitor X on SKU Y tends to undercut by 1p and changes price 5 times a day, etc. This is populated from the competitive data we fetch. Over time, this becomes a rich dataset of competitor behaviors.
All these tables together form our internal knowledge base. The data store doesn’t need to be overly complex given the scale (hundreds of SKUs), but designing it with clarity ensures we can scale to thousands of SKUs in future. The cache layer (e.g., a dictionary or a Redis if needed) would mirror some of this data in memory for quick access, especially the Current State for each SKU and the last API call times. Storage and Retrieval Operations: Typical operations include:
On fetching new data for SKU(s), update the Current State table and append to Historical table.
The strategy engine reads from Current State (and possibly Strategy Config) for its logic.
When a SKU is flagged unsavable or a strategy flag changes, update the Products/Config tables so that state persists.
When logging decisions, insert into Decision Log table.
Periodic archival: older historical data could be archived or pruned if space is a concern (or kept indefinitely for AI training possibilities).

Extensibility and Future Enhancements
The architecture and design outlined above ensure a solid foundation for rule-based repricing. Importantly, we have kept the system modular and future-proof for advanced upgrades, including AI-driven strategies and reinforcement learning, as mentioned by the user’s requirements. Here’s how the system can be extended:
Pluggable Strategy Module: The current rule-based Strategy Engine can be abstracted behind an interface (e.g., a function determine_new_price(state)). In the future, an AI module (say a machine learning model or a reinforcement learning agent) could replace or augment this function. For example, a reinforcement learning agent could observe the state (prices, competition) and reward outcomes (sales, profit) from the logs to learn an optimal pricing policy. The system’s rich logs and state history would provide excellent training data for such a model. We could start by running the AI in “shadow mode” (it suggests prices while the rule engine still makes the real call, to compare performance) and gradually trust it for live decisions. The modular design (where the engine reads from the database and outputs a decision) makes this swap relatively straightforward.
Scalability: With growth beyond a few hundred SKUs, we might need to distribute tasks or scale the database. The design can scale vertically (faster machine, more threads) or horizontally by separating concerns: e.g., run data fetching in one process, and price evaluations in parallel workers. Using a task queue like Celery or Amazon SQS could allow distributing workload if needed. The database can be upgraded to a full SQL server or a cloud database if the volume grows. The architecture diagram components could be split into microservices (e.g., a dedicated service for repricing decisions), but for now a single application is sufficient.
User Interface: Although not in scope, one could add a small UI or config file for the user to adjust strategy parameters (like minimum margins, or toggling certain strategies). Because the strategy configs are in a database, an interface to edit those would be a logical addition.
Additional Data Inputs: We can incorporate more data into pricing decisions, like Amazon’s Sales Rank, product page traffic, or even external market prices (if this were a multichannel repricer). The system can be extended to fetch such data (respecting their own APIs’ limits) and include them in the state for decision making (for example, if sales rank is dropping despite low price, maybe the issue isn’t price but something else – not directly for repricing, but good to know).
Serverless/Event-Driven Possibilities: In the future, parts of the system might be moved to an event-driven model using AWS tools (for instance, receiving SP-API notifications via an SQS queue and using AWS Lambda to trigger our logic). However, since the requirement is a local system, we stick to local scheduling. Still, the modular design could let us swap the data source from “poller” to “push” events easily for certain data.
By implementing the system with clean separation of concerns (fetching, deciding, updating, logging), we ensure that improvements or new algorithms can be integrated with minimal disruption. The ultimate goal is a system that not only reacts to the current market but learns and improves, staying one step ahead of competitors. With this design, the user will have a powerful local repricing solution that is comprehensive now and ready for smarter enhancements in the future.
